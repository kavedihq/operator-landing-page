How Kavedi works

The technical documentation. Updated October 7, 2026
At a glance
  • A Node.js server holds one linked-device WhatsApp connection per account and runs every engine: agents, bookings, scheduling, notifications.
  • A React web app (computer and phone) is served by the same server, on the same address as its API.
  • All state lives in Postgres. Sessions, contacts and message text are encrypted with AES-256-GCM.
  • AI answers come from open-weight models, only from what the account was taught, and hand over instead of guessing.

Architecture

PartWhat it is
ServerNode.js and Express, one long-running process. WhatsApp needs a persistent connection, so it can’t run serverless.
Web appVite and React, built into the server’s static files. The API is on the same origin, so there is no cross-origin traffic.
DatabasePostgres (Supabase), in Frankfurt. Row level security is on for every table with no public policies: only the server reads and writes.
Sign-inSupabase Auth: Google, email and password, or an email link. Every API request carries a session token that the server verifies. The account is the signed-in user.
Websitekavedi.com is a static site on Cloudflare. Its sign-in pages are passed through to the app.

The code is split by what each part is. The WhatsApp channel is the only place that knows the WhatsApp protocol. Platform (storage, encryption, time zones, settings), AI, conversation, automation, booking and agents sit on top, and dependencies only point downwards. That boundary is what would let an official WhatsApp Cloud API connection replace the linked device later without touching the rest.

The WhatsApp connection

  • Linked device. Kavedi uses an open-source implementation of the WhatsApp Web multi-device protocol, pinned to an exact version. It pairs with a phone-number pairing code, so the owner never has to scan their own screen.
  • Session storage. The device’s keys and credentials are stored in Postgres, encrypted. Routine key changes are saved in 15 second batches and flushed on shutdown, and new keys and credentials are saved at once. A restart reconnects without pairing again.
  • One connection per number. A Postgres lease, renewed every 20 seconds, means only one server ever holds a number, deploys included. A number can belong to one account only.
  • Groups, statuses, broadcast lists and Channels are acknowledged and dropped before decryption, unless an agent picked that group (three at most).
  • Presence. Not shown online on connect. Online and typing only when replying to someone who just wrote, then offline again. No typing indicator before scheduled or automatic messages.
  • Reconnects back off from 5 seconds, doubling to 10 minutes with jitter, and stop when the device was logged out, replaced or refused.
  • No buttons or list messages. They aren’t available on the linked-device protocol, so choices are numbered and read back from “1”, “the second one” or the words.

What happens to a message

In this order. The first step that applies decides.

  1. Duplicates are dropped by message id (WhatsApp sometimes delivers twice).
  2. A group message goes to group agents only, on exact words, at most once a minute and 10 runs an hour per group.
  3. A message the owner sent marks the chat as theirs for the pause time, and only agents set to start on the owner’s words can run.
  4. STOP and other opt-out words are recorded and end there.
  5. A team-wide kill switch, a chat set to Only you reply, or text that matches something a Kavedi wrote in the last day (another bot answering) all stop here. The last goes to the owner.
  6. A reply to a question an agent asked goes to that agent.
  7. A person with an open handover inside the quiet window is left alone by agents that answer anything.
  8. A welcome agent for someone new, then at most one other agent, oldest first: exact matches are checked first, then one small-model call picks among the agents started by meaning.
  9. One reply per message. If an agent sent something, that is the answer.
  10. Otherwise the first agent set to take whatever is left (the Receptionist), after the owner’s head start, and only if they haven’t replied within the pause time.

Every reply counts against a per-chat cap (6 in 3 minutes, 10 in 10). Over it, agents stop in that chat and it is handed to the owner with the reason.

Agents

An agent is a start, numbered steps of eight kinds, what it knows, and its rules.

  • Starts: a message that means something (a purpose sentence plus examples), certain words (sent by them, the owner or anyone), a kind of media, someone new, before or after a booking, someone quiet for N days, a handover from another agent, or whatever nothing else took.
  • Steps: Instructions, Say, Ask, If, Do, Run, Hand over, End. A run keeps named values ({service}, {times}, {reply}) for later steps. Up to 20 steps, 3 questions, 3 nested runs, and never an If inside an If.
  • Instructions run in one of two modes. With no tools and nothing to find out, one answer from the reply engine. With @mentioned tools (free times, book, move or cancel, send later, label) or values to collect, a conversation loop: up to 4 tool rounds per message, one message out per turn, the state kept encrypted between messages, and two ways out (done, or stuck, which hands over or runs the exception steps). It can only book a time a free-times lookup returned, and the slot is checked again before booking.
  • Do includes web requests: https only, port 443, every resolved address checked public, redirects followed by hand and checked again, 8 second and 5 MB limits, 500 a day per account. API keys are encrypted and only ever sent to the host they were saved for.
  • The four agents every account starts with are built from these same pieces. Their switches are the settings they always had (AI replies, booking, reminders, follow-ups), so the rest of the system reads one source of truth.
  • Agents can be shared as a compact code or a file. Shared agents arrive switched off, without anything that belongs to an account (groups, keys, ids), and say who they would talk to.

AI

  • Models. Replies are written by open-weight models (gpt-oss 120b, then smaller ones) on Groq. When those are unavailable, the same request can go to backup providers. Models with built-in web search are deliberately not used, so an answer can’t come from the internet instead of the owner.
  • Grounded answers. The model gets the owner’s profile, the closest knowledge entries and the agent’s rules, and answers in JSON. It must say when it doesn’t know, and may never invent a price, a time, a date, an address or a rule. A model failure is treated as “didn’t know”, never as an answer.
  • Language. It replies in the language the person wrote in, and understands Pidgin, slang and typos.
  • Matching by meaning is a small, temperature 0 call that returns one agent or none, and leans to none when unsure.
  • Embeddings and document reading use Gemini. Documents become draft answers the owner checks before anything is saved.
  • Voice notes are only transcribed when the owner presses Transcribe (Whisper).
  • Usage is counted per account and per purpose, in credits of 1,000 tokens, with an hourly limit per account.

Knowledge and retrieval

Each answer is stored with its label, content, topic and other ways people ask it, and embedded on write. Retrieval is cosine similarity in Postgres (pgvector), the top few entries per question. An agent can read all of Knowledge, some topics (every answer in them), or only its own notes. Answers can be sent word for word, with names filled in, or in the agent’s own words. Each answer counts how often it was used.

Handovers and the Inbox

  • A handover records who, the question, and why, and keeps an encrypted copy of the conversation that led to it.
  • An agent that doesn’t know asks “want me to pass this on?” and remembers the question for 30 minutes. A plain yes hands it over. Asking for a person, or one of the owner’s own cases, hands over at once.
  • While a handover is open, agents that answer anything leave that person alone for the account’s quiet window (12 hours by default, or until Done).
  • Replies from the app go out as WhatsApp replies quoting the exact message.

Things on the clock

  • The queue. Scheduled messages, reminders, follow-ups and broadcasts are rows in one Postgres queue, polled every 30 seconds and claimed atomically, so a message is never sent twice, even while two servers overlap during a deploy. Anything more than 2 hours late is skipped, not sent late.
  • Repeating messages queue each occurrence through the same checks as one sent by hand. A label is read when it sends, so people added later get the next one.
  • Broadcasts go one message at a time in bursts of 10 to 15, 20 to 75 seconds apart, with 2 to 5 minute pauses, between 8am and 8pm, 50 a day, only to people who have messaged the number, never to anyone who opted out.
  • Follow-ups go once per quiet spell, 9am to 7pm, never to someone with a question waiting, a booking coming up, something already queued or an opt-out.

Bookings

Availability is a pure function of services, weekly hours, breaks, time off, rules and existing bookings, given a clock rather than reading one, so it is fully tested, daylight saving included. Time zones are IANA names per account, handled with the platform’s own Intl data. Double booking is refused by a database constraint rather than checked first. Who added each booking (a chat, the owner, the assistant) is recorded. Connected calendars add their busy times.

Connected apps

  • Calendar link: a private iCalendar feed (180 days ahead, no phone numbers). The secret is stored hashed to find the account and encrypted to show it again, and can be replaced.
  • Google Calendar: OAuth with the single calendar.events scope. Bookings are written as events tagged with the booking’s id, busy times are read before offering slots, and access is revoked with Google on disconnect or account deletion.
  • Stripe and Paystack: payment links for a fixed amount, stored in minor units, never floats. Paid is learned from signed webhooks, with a check against the provider when the page opens in case a webhook was missed. Keys are encrypted. Money goes directly to the owner’s account.

Notifications

Web push (VAPID) to every device the owner turned on, and email through Resend: someone waiting (gathered 20 seconds into one), new bookings, a payment, and WhatsApp going down for 10 minutes and coming back. These go outside WhatsApp, so a dropped connection still reaches the owner. The app installs as a progressive web app, and its icon shows how many people are waiting.

The encryption key is never stored in the database. Deleting an account removes every row for it and the sign-in itself. The full detail is in the privacy policy.

Security

  • Every app request is checked against a verified session. During the beta, only approved emails can use the app.
  • Strict headers on every response: no framing, no sniffing, HSTS, a tight permissions policy, no caching of API responses.
  • Rate limits on sign-in, pairing codes (30 seconds apart, 5 per 15 minutes), dictation, tests and public endpoints.
  • No third-party “anti-ban” packages, which have been caught stealing WhatsApp sessions.
  • Found a problem? Email support@kavedi.com.

Some things are not settings: never inventing an answer, handing over to a person, never answering a group with AI, and never starting a chat on its own.

Reliability

  • Each account’s connection is isolated: one failing never takes down the process.
  • On start, stored sessions reconnect staggered, so a restart is not a reconnect storm.
  • A failed read never makes Kavedi louder: if settings or agents can’t be read, it stays quiet rather than guessing.
  • Missed webhooks, expired questions and old messages are cleaned up on timers.
  • Kavedi is in beta. Expect changes, and tell us what breaks.
